# Yandex Cloud: аварийная миграция arhDesign

Статус: **accepted**, 3 ноября 2026 года. Вариант одной production-ВМ подтверждён
владельцем проекта. Документ заменяет инфраструктурную
часть решения [`beget-three-vps.md`](./beget-three-vps.md) после аварии Beget.
Прикладные границы edge/API/data сохраняются как Docker-сервисы, но для
аварийного старта размещаются на одной ВМ. Разделение на три ВМ остаётся
следующим этапом масштабирования, а не обязательным условием запуска.

## Контекст и ограничения

- Production должен снова работать в России без Cloudflare proxy.
- На старте ожидается до 2 000 зарегистрированных пользователей; подтверждённый
  локальный профиль — до 100 одновременно активных пользователей и 50 req/s в
  коротком пике. Производительность облачных ВМ ещё не измерена.
- PostgreSQL и файловые данные остаются self-hosted; managed PostgreSQL не
  используется.
- Единственная публичная точка приложения — reverse proxy на общей ВМ. Порты
  API и PostgreSQL не публикуются. Будущие Prometheus/Grafana также должны быть
  доступны только через аутентифицированный reverse proxy, а не прямые порты.
- DNS переключается только после восстановления backup, smoke test по
  временному адресу и проверки Telegram. Старый контур сохраняется для rollback.

## Конфигурации и стоимость

Расчёт получен в консоли Yandex Cloud 3 ноября 2026 года для 720 часов в месяц,
с НДС. Исходящий трафик сверх бесплатного объёма и фактически занятое backup
storage считаются отдельно.

### Рекомендуемый аварийный production: одна ВМ

| Узел | Конфигурация | Сеть и backup | ₽/мес. |
| --- | --- | --- | ---: |
| `arh-prod-01` | 4 vCPU, 50%, 8 ГиБ RAM, 100 ГиБ network SSD | статический public IPv4, ежедневный Cloud Backup | 5 964,13 |

В сумму включены вычисления, RAM, диск, активный IPv4 и подключение одной ВМ к
Cloud Backup. Фактически занятое backup storage и платный исходящий трафик
считаются отдельно. Первый deploy запускает отдельные Docker-сервисы:
Caddy/Next.js, Go API и Telegram worker, PostgreSQL и backup worker.
Prometheus/Grafana и отдельное файловое хранилище остаются следующими задачами.
Для PostgreSQL задаются отдельный volume, лимиты памяти и healthcheck; публичный
доступ к `5432`, `8080`, `3000` и портам мониторинга запрещён.

Одна ВМ уменьшает стоимость и время аварийного восстановления, но является
единой точкой отказа. Поэтому обязательны ежедневный Cloud Backup, логический
PostgreSQL backup и независимая зашифрованная копия вне этой ВМ. При устойчивом
росте нагрузки сначала выносится PostgreSQL, затем API/worker и file storage.

## Сетевые границы первой версии

| Security group | Входящий трафик | Исходящий трафик |
| --- | --- | --- |
| `arh-edge` | TCP 80/443 из интернета; TCP 22 только для key-only deploy | DNS/NTP, HTTPS, SMTP и Telegram proxy |
| `arh-api` | не используется до выноса API | PostgreSQL, SMTP/HTTPS и Telegram proxy SSH |
| `arh-data` | не используется до выноса data | DNS/NTP/HTTPS через ограниченный proxy/NAT путь |

Резервируется один статический публичный IPv4 для общей ВМ. DNS публикует только
его. PostgreSQL слушает внутреннюю Docker-сеть и не публикует порт на хосте.

## Backup и восстановление

На 3 ноября 2026 года edge/API Beget не отвечают по SSH. Последний подтверждённый
workflow dump создан 30 октября 2026 года, но был сохранён только в Docker volume
data-узла (`OFFSITE_BACKUP_ENABLED=false`). Пока Beget недоступен, этот dump и
актуальная PostgreSQL недоступны для переноса. DNS cutover на новую пустую БД
требует отдельного решения владельца либо восстановления доступного backup.

1. До миграции создать логический PostgreSQL backup и checksum на Beget.
2. Передавать backup на новую ВМ по SSH, без публикации БД.
3. Восстановить backup в новую PostgreSQL 17 и проверить row counts, миграции,
   авторизацию, проекты, заявки и Telegram bindings.
4. Включить ежедневный Cloud Backup общей VM. Он ускоряет восстановление узла, но
   не заменяет логический PostgreSQL backup.
5. До удаления Beget хранить независимую зашифрованную копию вне общей ВМ.
   Backup только в том же облаке не защищает от отказа аккаунта или провайдера.

## Порядок cutover и rollback

1. Создать VPC, security group, один статический public IP и одну ВМ.
2. Развернуть Docker, восстановить PostgreSQL и файлы, затем API и frontend.
3. Проверить edge через временный host override: `/`, `/readyz`, вход,
   регистрацию, проект, форму, Telegram и запись/чтение БД.
4. Уменьшить TTL `@` и `www` до 300, если это ещё возможно до cutover.
5. Заменить обе A-записи на статический IPv4 нового edge.
6. Проверить authoritative DNS, публичные resolver, TLS и полный smoke test.
7. Наблюдать минимум 24 часа. Beget не выключать и данные там не удалять.

Rollback до появления новых записей в Yandex Cloud: вернуть A-записи Beget.
После появления новых записей нужен краткий режим read-only либо обратная
миграция данных; простая смена DNS может потерять записи, созданные после cutover.

## Критерии пересмотра

- устойчивый CPU p95 выше 70% или RAM выше 75%;
- data disk заполнен выше 70%;
- более 100 одновременно активных пользователей или 50 req/s;
- требования HA/RTO, которые не выполняются одной зоной;
- рост файлов требует отдельного object storage;
- стоимость трёх ВМ становится выше managed/HA альтернативы с сопоставимым SLA.
