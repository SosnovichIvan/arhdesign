# План внедрения личного кабинета по версиям

Статус: **R1 accepted 2026-09-22; R2–R7 proposed**. Документ делит реализацию
личного кабинета на семь последовательных релизов. Номер следующего релиза
отсчитывается от текущей версии приложения `0.1.0`.

## 1. Общий принцип поставки

Каждый релиз является законченным вертикальным срезом: пользовательский путь,
данные, серверные права, интерфейс, уведомления, тесты и эксплуатационная
документация поставляются вместе. Нельзя считать версию завершённой только по
готовому макету или работающему happy path.

| Релиз | Версия | Основной результат | Зависит от |
| --- | --- | --- | --- |
| R1 | `0.2.0` | Авторизация, регистрация, email-flow и создание проекта | текущий публичный сайт |
| R2 | `0.3.0` | Участники проекта и задачи | R1 |
| R3 | `0.4.0` | Финансы проекта: поступления и расходы | R1–R2 |
| R4 | `0.5.0` | Материалы, поставщики и связь с расходами | R3 |
| R5 | `0.6.0` | Проектный и общий календарь | R2–R4 |
| R6 | `0.7.0` | Глобальные, проектные и контекстные чаты | R2–R5 |
| R7 | `0.8.0` | Сводки по проектам и сотрудникам | R2–R6 |

После стабилизации `0.8.0` кабинет может быть выпущен как `1.0.0` отдельным
решением. Перенос незавершённой функции в следующий релиз фиксируется явно;
скрытое исключение обязательных проверок не допускается.

## 2. Definition of Done каждого релиза

### 2.1 Дизайн

- В Figma отрисованы все маршруты релиза и переходы между ними.
- Для каждого пути показаны: default, loading, empty, success, validation error,
  server error, forbidden/read-only и disabled-состояния.
- Зафиксированы различия ролей и привилегий, опасные действия и подтверждения.
- Проверены desktop, tablet и mobile, светлая и тёмная темы.
- Описаны focus, keyboard-путь, длинный контент, переполнение таблиц и
  reduced-motion. Контраст значимых элементов соответствует правилам проекта.
- Frame и сценарии имеют стабильные названия; Node ID внесены в документацию.

### 2.2 Документация

- Обновлены пользовательские сценарии и каталог маршрутов.
- Описаны backend-контракты, OpenAPI, коды ошибок и правила авторизации объекта.
- Для новых данных описаны владелец, ограничения, миграция, индексы, аудит,
  retention и восстановление после частичного сбоя.
- Зафиксированы email/Telegram/background-события, идемпотентность, retries и
  поведение при недоступности внешнего сервиса.
- Составлен тест-план с трассировкой «требование → автоматическая проверка».
- README и эксплуатационные инструкции обновлены, если появились новые env,
  секреты, миграции, worker-процессы или действия при развёртывании.

### 2.3 Схема данных до реализации

- До написания миграций для релиза согласуется концептуальная и физическая
  модель данных: сущности, владелец, идентификаторы, связи и кардинальности.
- На странице Figma `09 — Client Cabinet / Data Model` размещается ERD с
  выделением сущностей текущего релиза, уже выпущенных и будущих зависимостей.
- В репозитории ведётся версионируемая Mermaid ERD и data dictionary. Именно
  документация и применённые миграции являются источником истины; Figma служит
  удобным визуальным представлением и не заменяет DDL.
- Для каждой таблицы заранее фиксируются: сценарий, owner/tenant scope,
  nullability, uniqueness, foreign keys, delete policy, аудит, retention,
  ожидаемый рост и чувствительность данных.
- Для денег описываются валюта и минимальная денежная единица, для времени —
  UTC/timezone semantics, для файлов — metadata и внешний объект хранения.
- Для каждого индекса указывается обслуживаемый запрос, порядок колонок и цена
  записи. Схема не утверждается списком индексов без запросов.
- ERD не содержит реальные персональные данные, пароли, токены или production ID.
- Изменение согласованной схемы после начала разработки требует обновить ERD,
  data dictionary, миграционный план и тесты совместимости.

Минимальный срез данных по релизам:

| Релиз | Концептуальные сущности |
| --- | --- |
| R1 | пользователь, профиль, роль, сессия, email/password token, проект, участник проекта, audit event |
| R2 | privilege, задача, исполнитель, комментарий, история статуса, выплата по задаче |
| R3 | поступление, запрос на расход, решение, ledger operation, корректировка, attachment |
| R4 | материал, поставщик, поставка, material-expense allocation, версия материала |
| R5 | событие, встреча, календарный источник, связь события с проектом/задачей/поставкой |
| R6 | чат, участник чата, сообщение, read marker, context link, notification receipt |
| R7 | шаблон фильтра сводки; результаты строятся запросом и не сохраняются snapshot-таблицей |

### 2.4 Код и автоматические проверки

- Реализованы frontend, backend и PostgreSQL-миграции в границах релиза.
- Сервер проверяет права на действие и конкретный проект/объект. Скрытие кнопки
  на frontend не считается защитой.
- Unit, component, service, repository и integration-тесты покрывают happy path,
  валидацию, запрет доступа, повтор запроса, конкурентные изменения и rollback.
- Для изменённого авторского кода действует порог проекта: не менее 90% строк и
  ветвей там, где метрика поддерживается. DDL проверяется сценариями PostgreSQL.
- Cypress покрывает пользовательские пути релиза. Селекторы основаны на
  доступных именах или стабильных `data-cy`, а не на CSS-структуре.
- Любая новая или изменённая пользовательская логика считается незавершённой,
  пока каждый достижимый UI-сценарий не связан с Cypress-тестом: happy path,
  client/server validation, loading/disabled, empty, retry/fallback, forbidden,
  expired и повтор действия. Исключение допускается только как явно
  согласованный и документированный технический сценарий, недоступный браузеру.
- Для каждого релиза поддерживается scenario matrix `требование → состояние →
  Cypress spec`; отсутствие строки или автоматической проверки блокирует QA gate.
- Существующие Playwright-тесты не удаляются: они входят в полную регрессию.

### 2.5 Визуальное ревью и выпуск

- Реализация сопоставлена с Figma на 1440, 768 и 390 px в обеих темах.
- Проверены клавиатура, focus, масштабирование текста, axe и reduced-motion.
- Выполнены lint, typecheck, frontend coverage, backend tests/race, PostgreSQL
  migration tests, Cypress, существующий Playwright и production build.
- Проведён ручной smoke-test на локальном Docker-окружении.
- Изменения проходят рабочая ветка → PR в `develop` → PR `develop` в `main`.
- Deployment запускается только версионным тегом на коммите из `main`.
- Для миграций и внешних эффектов описаны rollback/recovery и совместимость
  старой/новой версии приложения.
- Перед релизом с изменением схемы создан свежий backup и пройден restore drill
  согласно [`postgresql-backup-and-recovery.md`](../operations/postgresql-backup-and-recovery.md).
- Размер production VM подтверждён нагрузочным тестом и сверяется с порогами
  [`client-cabinet-capacity-plan.md`](client-cabinet-capacity-plan.md).

Планируемый набор команд после подключения Cypress:

```bash
npm run lint
npm run typecheck
npm run test:coverage
npm run test:ui
npm run test:e2e
npm run build
(cd apps/api && go vet ./... && go test -race -count=1 ./...)
TEST_DATABASE_URL=postgres://.../arhdesign_test?sslmode=disable npm run validate:api-adapter
```

`test:ui` резервируется за Cypress, `test:e2e` сохраняется за существующим
Playwright-набором.

## 3. R1 / `0.2.0` — учётная запись и проекты

### Пользовательские пути

- регистрация: логин, email, пароль, подтверждение пароля, имя, необязательные
  отчество/фамилия и профессиональная роль;
- подтверждение email, повторная отправка письма, истёкшая/недействительная ссылка;
- вход по логину и паролю, выход, восстановление сессии;
- запрос восстановления пароля и установка нового пароля;
- вход главного администратора существующими системными учётными данными;
- защищённая главная страница: список проектов, empty state и создание проекта;
- супер-администратор создаёт и ведёт проект без заказчика, а заказчика можно
  назначить позднее без потери истории;
- супер-администратор видит список пользователей, дату регистрации и активность,
  может отключить или восстановить доступ к платформе;
- создатель проекта становится администратором заказа; создание супер-админом
  не создаёт фиктивного заказчика;
- переключатель автосогласования расходов создаётся включённым, но до R3 не
  запускает финансовые операции.

Маршруты: `/login`, `/register`, `/verify-email`, `/forgot-password`,
`/reset-password`, `/account/projects`, `/account/projects/new`, `/account/users`.

### Реализация и данные

- пользователи, профиль, расширяемый справочник ролей, email verification tokens,
  password reset tokens, сессии/refresh-механизм и статус блокировки;
- проекты, обязательный создатель, необязательный единственный активный
  заказчик, администраторы, даты, тип, валюта и описание;
- хеширование паролей, rotation/expiry токенов, rate limits, generic-ответ на
  восстановление пароля и аудит security-событий;
- SMTP-конфигурация и шаблоны писем подтверждения/восстановления.

### Cypress

- регистрация → письмо перехвачено тестовым SMTP → подтверждение → вход;
- duplicate login/email, слабый пароль, несовпадение паролей;
- неподтверждённая учётная запись и повторная отправка письма;
- успешное восстановление, истёкшая и повторно использованная ссылка;
- login/logout/session restore и redirect с защищённого маршрута;
- пустой список проектов → создание → появление карточки;
- супер-администратор создаёт заказ без заказчика, ведёт задачи и настройки,
  затем назначает заказчика с сохранением прежней истории;
- супер-администратор отключает пользователя, активная сессия отзывается, после
  восстановления доступа пользователь снова может войти;
- другой пользователь не открывает чужой проект по прямому URL.

### Не входит

Участники проекта, задачи, финансы и рабочие разделы проекта остаются
недоступными либо отображаются как «Будет доступно позже».

## 4. R2 / `0.3.0` — участники и задачи проекта

### Пользовательские пути

- добавление пользователя в проект по логину или email;
- назначение роли в проекте и объектных привилегий;
- создание, просмотр, редактирование и назначение задачи;
- статусы, дедлайн, фактическое время старта/завершения и выплата исполнителю;
- комментарии заказчика, проверка, принятие или возврат задачи;
- заказчик помечает проект к удалению, супер-администратор выполняет удаление;
- администратор заказа имеет все права проекта, кроме удаления проекта.

Маршруты: `/account/orders/[orderId]`, `/account/orders/[orderId]/members`,
`/account/orders/[orderId]/tasks`, `/account/orders/[orderId]/tasks/new`,
`/account/orders/[orderId]/tasks/[taskId]`.

### Реализация и данные

- membership, роль в проекте, наборы privileges и серверный `Can(user, order, action)`;
- задачи, назначения, статусы, дедлайны, start/end time, выплаты, комментарии и
  история изменений;
- optimistic locking/version для конфликтующего редактирования;
- аудит назначения, изменения прав, статуса, сроков и выплат.

### Cypress

- администратор добавляет участника и создаёт задачу;
- исполнитель видит только назначенную задачу и разрешённые действия;
- заказчик видит историю, комментирует, принимает или возвращает результат;
- участник без права не видит кнопку и получает `403` при прямом запросе;
- администратор заказа не может удалить проект;
- снятие доступа немедленно закрывает проект и прямую ссылку задачи;
- конфликт двух редакторов показывает безопасное сообщение без потери данных.

## 5. R3 / `0.4.0` — финансы проекта

### Пользовательские пути

- создание поступления от заказчика;
- создание расхода/запроса на расход, редактирование черновика и отмена;
- автосогласование, включённое по умолчанию, либо ручное согласование заказчиком;
- подтверждение оплаты, возврат и корректирующая операция;
- прикрепление счёта, чека, акта или другого подтверждающего файла;
- просмотр поступлений, подтверждённых расходов, доступного остатка, журнала
  операций и ожидающих решений.

Маршруты: `/account/orders/[orderId]/financials`,
`/account/orders/[orderId]/financials/incomes/new`,
`/account/orders/[orderId]/expense-requests/new`,
`/account/orders/[orderId]/expense-requests/[expenseId]`.

### Реализация и данные

- immutable ledger финансовых операций, expense requests, approvals, attachments;
- деньги хранятся в `NUMERIC(14,2)` с явной валютой и единым правилом округления;
- подтверждённая запись не переписывается: исправление создаёт связанную
  корректировку и аудит;
- серверные права `financials.view/create/update/approve/delete`;
- проверка файлов: размер, MIME, безопасное имя, закрытое хранение и доступ по
  авторизованной краткоживущей ссылке.

### Cypress

- поступление изменяет доступный остаток только после подтверждения;
- автосогласованный и ручной сценарии расхода;
- согласование/отклонение заказчиком с комментарием;
- в заказе без заказчика супер-администратор согласует расход и добавляет
  поступление без создания фиктивной клиентской учётной записи;
- прикрепление и открытие разрешённого файла, запрет чужому пользователю;
- итоги совпадают с журналом после возврата и корректировки;
- повтор submit не создаёт двойной расход;
- read-only пользователь видит данные без управляющих действий.

## 6. R4 / `0.5.0` — материалы проекта

### Пользовательские пути

- добавление, редактирование и мягкое удаление материала;
- поставщик, контакты, договор, сумма, оплачено, статус и дата доставки;
- связь материала с задачей, расходом и подтверждающими файлами;
- исполнителю отдельно выдаются права просмотра/создания/редактирования/удаления;
- переход из материала к расходу и обратно без дублирования суммы.

Маршруты: `/account/orders/[orderId]/materials`,
`/account/orders/[orderId]/materials/new`,
`/account/orders/[orderId]/materials/[materialId]`,
`/account/orders/[orderId]/materials/[materialId]/edit`.

### Реализация и данные

- материалы, поставщики, material-expense allocations, поставки и версии записей;
- инвариант связи с ledger: оплаченный расход отражается в материале, но не
  создаётся второй финансовый факт;
- отдельные privileges на create/update/delete и полный аудит удаления;
- доставка хранит статус и ожидаемую/фактическую дату.

### Cypress

- CRUD материала и валидация обязательных полей;
- назначенный исполнитель с правом редактирует, без права получает `403`;
- связь с расходом отображается с обеих сторон;
- изменение статуса и даты доставки сохраняется в истории;
- удалённая запись исчезает из активного реестра, но не ломает финансовый аудит;
- фильтрация/пустое состояние/длинные названия и таблица на узком экране.

## 7. R5 / `0.6.0` — календари

### Пользовательские пути

- календарь проекта: задачи, события, встречи, сроки и поставки;
- создание события или задачи из календаря;
- общий календарь/таймлайн всех доступных проектов с фильтром проектов;
- переход из события в проект, задачу, материал или поставку;
- видимость строго по роли и объектным привилегиям.

Маршруты: `/account/calendar`, `/account/orders/[orderId]/calendar`.

### Реализация и данные

- календарные события и источники событий; задачи/поставки не дублируются, а
  проецируются в календарь через стабильную ссылку на источник;
- хранение времени в UTC, отображение в часовом поясе профиля;
- стабильная выборка по диапазону, проекту и доступу пользователя;
- обновление дедлайна синхронно меняет представление календаря.

### Cypress

- empty state без проектов;
- создание события и задачи из проектного календаря;
- общий календарь показывает только доступные проекты;
- фильтр проектов и переход к исходной сущности;
- перенос через границу месяца, timezone и событие на весь день;
- снятие доступа удаляет событие из общего календаря и запрещает прямой URL.

## 8. R6 / `0.7.0` — чаты и обсуждения

### Пользовательские пути

- личный и групповой глобальный чат; у группы обязательно название;
- общий чат проекта;
- контекстный чат задачи, расхода или материала из соответствующей таблицы;
- добавление участника по логину/email без выдачи доступа к проекту;
- Telegram-уведомления авторизованному подписанному пользователю о событиях,
  которые относятся к нему и доступны на момент отправки.

Маршруты: `/account/chats`, `/account/orders/[orderId]/chat`,
`/account/orders/[orderId]/discussions/[contextType]/[contextId]`.

### Реализация и данные

- chats, participants, messages, read markers и context link;
- единственный контекстный чат по `(order_id, context_type, context_id)`;
- повторная серверная проверка доступа при чтении, отправке и уведомлении;
- удаление участника из проекта немедленно закрывает проектные обсуждения;
- доставка сообщения и Telegram выполняются раздельно: сбой Telegram не
  откатывает сохранённое сообщение, повтор уведомления идемпотентен.

### Cypress

- личный чат, групповой чат с названием и валидация пустого названия;
- общий чат проекта только для участников;
- создание чата из строк задачи, расхода и материала;
- повторное действие открывает существующий чат, не создавая дубликат;
- глобальный собеседник без доступа не открывает ссылку сущности проекта;
- снятие прав закрывает историю контекстного чата;
- offline/retry UI не дублирует сообщение.

## 9. R7 / `0.8.0` — сводки по проектам и сотрудникам

### Пользовательские пути

- супер-администратор открывает месячную сводку задач;
- группировка по проектам или выбранным сотрудникам;
- старт, завершение, фактическое время, статус и выплата по каждой задаче;
- выбор сотрудников/проектов и сохранение фильтра как шаблона;
- повторное применение шаблона пересчитывает актуальные данные;
- переход из строки сводки в задачу или проект.

Маршруты: `/account/reports/tasks`, `/account/reports/tasks/new`.

### Реализация и данные

- шаблон хранит только фильтр, владельца и выбранные колонки, но не snapshot
  результатов;
- агрегации считаются сервером с обязательным scope по доступным проектам;
- права `reports.tasks.manage` доступны супер-администратору; будущая выдача
  другим ролям не требует изменения модели данных;
- индексы и планы запросов проверяются на представительном объёме задач.

### Cypress

- сводка за месяц по выбранным сотрудникам;
- группировка по проекту и переход к строке задачи;
- сумма выплат и часов соответствует исходным задачам;
- сохранение, повторное применение, переименование и удаление шаблона;
- шаблон пересчитывает новые данные и не показывает удалённый из доступа проект;
- обычный администратор проекта и исполнитель не открывают раздел по прямому URL;
- empty state, длинный список сотрудников и перенос filter chips.

## 10. Сквозные quality gates

| Gate | Что блокирует релиз |
| --- | --- |
| Design review | отсутствует путь, состояние, роль, адаптив или тема |
| Security review | объектные права проверяются только на frontend; токены/пароли попадают в логи |
| API review | не описан контракт, ошибка, идемпотентность или совместимость |
| Database review | миграция не проверена на PostgreSQL, нет recovery или нарушена целостность |
| Data model review | ERD/data dictionary не согласованы с миграциями, не определены ownership и delete policy |
| Backup review | копия хранится только на VPS, нет checksum/restore drill или превышены RPO/RTO |
| Test review | нет Cypress-пути, интеграционной проверки или coverage ниже политики |
| Visual review | расхождение с Figma, обрезка, недоступный focus/контраст |
| Regression | падает любой старый Vitest, Playwright, Go test, migration test или build |
| Delivery | PR обходит `develop`, тег не принадлежит `main`, нет rollback-плана |

## 11. Порядок подготовки каждого релиза

1. Создать отдельное изменение OpenSpec с proposal, design, specs и tasks.
2. Уточнить Figma-пути и согласовать дизайн до начала основного кода.
3. Отрисовать ERD в Figma, обновить data dictionary и согласовать модель данных.
4. Зафиксировать API и права; провести architecture/security/database review.
5. Добавить миграции и backend-контракты с тестами.
6. Реализовать frontend и component-тесты.
7. Добавить Cypress для всех путей релиза.
8. Создать pre-deploy backup, выполнить restore drill и проверить recovery.
9. Выполнить визуальное ревью и полную регрессию существующего продукта.
10. Обновить документацию эксплуатации и миграций.
11. Доставить через PR `feature → develop → main` и создать новый неизменяемый тег.

Релиз не смешивается со следующим: незавершённые маршруты скрываются feature
flag или не включаются в production build. Схема БД при поэтапном rollout
остаётся совместимой как минимум с предыдущей версией приложения.
