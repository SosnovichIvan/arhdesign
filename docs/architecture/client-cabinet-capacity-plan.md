# План мощности VM для личного кабинета

Статус: **R1 locally validated**. Анализ выполнен для R1–R7 и целевой аудитории
до 10 000 зарегистрированных пользователей. Локальный release-кандидат прошёл
профиль 100 virtual users / 50 req/s; production VM подтверждается отдельным
VPS soak и host metrics перед go/no-go.

Статус мониторинга и суточной Telegram-сводки: **accepted 2026-09-22**.

Дата проверки тарифов VDSina: **22 сентября 2026 года**.

| RAM | 8 ГБ |
| Диск | 150 ГБ NVMe |
| Сеть | порт 1 Гбит/с, включённый трафик 32 ТБ/месяц |
| ОС | Ubuntu 24.04 LTS, Docker/Compose |
| Размещение | Москва, Россия |
| Цена на дату анализа | 80 ₽/день, около 2 400 ₽/месяц |

Это максимальный фиксированный стандартный тариф из актуальной линейки
VDSina. Характеристики, цена, канал и российская локация опубликованы на
[официальной странице стандартных VPS](https://vdsina.ru/pricing/standard).
Перед заказом цену требуется проверить повторно.

Конфигурация рассчитана на один production-узел с Caddy, Next.js, Go API и
PostgreSQL. Она достаточна как стартовая только при профиле нагрузки из
раздела 2. Число зарегистрированных аккаунтов само по себе почти не определяет
мощность; критичны одновременно активные пользователи, запросы в секунду,
тяжесть отчётов, объём файлов и фоновые процессы.

## 2. Расчётные предположения

Для базовой конфигурации принимается:

- до 10 000 зарегистрированных аккаунтов;
- до 500 активных пользователей в день;
- до 100 одновременно работающих пользователей;
- до 25 HTTP-запросов/с продолжительно и до 50 запросов/с кратковременно;
- p95 обычного чтения до 500 мс, изменения данных до 800 мс;
- база данных до 30 ГБ;
- пользовательские чеки, договоры и другие вложения хранятся в отдельном
  российском S3-совместимом объектном хранилище, а не на системном диске VM;
- тяжёлые отчёты R7 имеют bounded queries, pagination и timeout;
- письма, Telegram и другие внешние эффекты выполняются через очередь/outbox и
  не удерживают HTTP-запрос или транзакцию БД.

Это целевые ограничения планирования, а не измеренная производительность. Если
ожидается 10 000 ежедневно активных или одновременно подключённых пользователей,
базовая VM не подходит без отдельного теста и масштабирования.

## 3. Почему не меньшая VM

Текущий production stack включает пять постоянно или периодически работающих
контейнеров: Caddy, Next.js, Go API, PostgreSQL и backup. В R1 добавятся сессии,
email-flow и проектные запросы; затем — задачи, финансы, материалы, календарь,
чаты и отчёты.

Ориентировочный бюджет памяти для VM с 8 ГБ:

| Потребитель | Рабочий бюджет |
| --- | ---: |
| ОС, Docker, Caddy, служебные процессы | 0,7–1,0 ГБ |
| Next.js runtime | 0,8–1,5 ГБ |
| Go API и фоновые workers | 0,3–0,8 ГБ |
| PostgreSQL и filesystem cache | 2,5–3,5 ГБ |
| backup, миграция и кратковременные пики | 0,5–1,0 ГБ |
| обязательный свободный запас | не менее 1,5 ГБ |

VM с 2–4 ГБ не оставляет безопасного запаса PostgreSQL и deployment-пикам.
Сборка образов уже выполняется в GitHub Actions и на VPS доставляются готовые
images, поэтому production VM не должна тратить RAM/CPU на `next build` и
компиляцию Go.

## 4. Диск и данные

150 ГБ распределяются как эксплуатационный бюджет, а не квота приложению:

- 20–30 ГБ — ОС, Docker images, layers и журналы;
- до 30 ГБ — PostgreSQL на первом этапе;
- до 15 ГБ — WAL, temporary files и запас миграции;
- до 15 ГБ — локальные краткосрочные backup;
- не менее 45 ГБ, то есть 30% диска, остаются свободными.

Предупреждение создаётся при 70% заполнения, критическое — при 80%. Автоматическая
очистка неиспользуемых images не должна удалять текущий и предыдущий release.
Файлы пользователей нельзя бессрочно складывать в Docker volume: они быстро
станут главным потребителем диска и помешают восстановлению PostgreSQL.

Основной и локальный backup на одной VM не защищают от потери узла. Обязателен
off-site backup по
[`postgresql-backup-and-recovery.md`](../operations/postgresql-backup-and-recovery.md).
Снимок VM VDSina может быть дополнительным уровнем, но не заменяет проверенный
PostgreSQL restore и независимую копию. Провайдер заявляет NVMe, резервные
копии/API и возможность увеличения тарифа на
[официальной странице VDSina](https://vdsina.ru/en/pricing/standard).

## 5. Рекомендуемые ограничения сервисов

Перед R1 необходимо задать и проверить container limits, чтобы один процесс не
выдавил PostgreSQL из памяти. Начальные значения уточняются тестом:

| Компонент | Начальный предел/настройка |
| --- | --- |
| Next.js | memory limit 2 ГБ, минимум 0,5 CPU |
| Go API + workers | memory limit 1 ГБ, минимум 0,5 CPU |
| PostgreSQL | memory limit 3,5–4 ГБ; `shared_buffers` 1,5–2 ГБ |
| Caddy | memory limit 256 МБ |
| PostgreSQL connections | общий budget 50–80; pool API не более 70% |
| Swap | 2–4 ГБ как аварийная защита, не как рабочая память |

`work_mem` нельзя умножать только на `max_connections`: оно выделяется на
операцию запроса. Значение и pool настраиваются после измерения реальных query
plans. Redis для R1 не требуется по умолчанию: сессии и durable rate limits
могут храниться в PostgreSQL. Redis вводится только при появлении измеренной
нагрузки или нескольких API replicas.

## 6. Пороги масштабирования

### Этап A — один узел

4 vCPU / 8 ГБ / 150 ГБ подходит, пока одновременно выполняются условия:

- CPU p95 ниже 70%, memory working set ниже 75%;
- swap не используется постоянно;
- PostgreSQL connections ниже 70% pool budget;
- p95 latency и error rate проходят критерии раздела 7;
- диск ниже 70%, I/O wait p95 ниже 10%;
- backup не ухудшает p95 более чем на 20%.

### Этап B — разделение приложения и БД

Переход требуется, если любой порог нарушается на двух последовательных
интервалах по 15 минут при штатной нагрузке или база приближается к 30–50 ГБ:

- VM приложения: 4 vCPU / 8 ГБ;
- отдельная VM PostgreSQL: 4 vCPU / 8 ГБ / 150 ГБ NVMe;
- private network, доступ БД только от приложения и backup-процесса;
- файлы — в российском object storage;
- Caddy и приложение масштабируются независимо от БД.

Стоимость двух стандартных VM по тарифу на дату анализа — около 4 800 ₽/месяц.
Разделение даёт isolation, но ещё не высокую доступность: каждая VM остаётся
single point of failure.

### Этап C — высокая параллельность

Для порядка 10 000 одновременно активных пользователей заранее нельзя обещать
одну конфигурацию. Нужны минимум два stateless application-узла за load balancer,
отдельная PostgreSQL с репликацией/проверенным failover, shared object storage,
централизованные sessions/rate limits, очередь workers и полноценный load test.
Как кандидат VDSina предлагает Hi-CPU от 8 vCPU / 16 ГБ / 320 ГБ за
256 ₽/день; актуальные параметры опубликованы в
[официальном перечне тарифов](https://vdsina.ru/plans-min-costs). Выбор такого
тарифа без профиля запросов и теста был бы необоснованным.

## 7. Нагрузочная приёмка R1

До публикации `0.2.0` выполнить k6 или эквивалентом три профиля на отдельной
среде с PostgreSQL объёмом не менее 10 000 пользователей и реалистичными
проектами:

1. 30 минут: 100 виртуальных пользователей, плавный набор и штатные сценарии.
2. 10 минут: кратковременный пик 200 виртуальных пользователей.
3. 60 минут: soak test с фоновой отправкой писем, retention и backup.

Сценарии: login/session refresh, список проектов, создание проекта, чтение
профиля и запрещённый доступ к чужому проекту. Email/Telegram тестируются через
управляемый mock с теми же timeout/retry правилами.

Критерии:

- error rate ниже 1%, исключая ожидаемые `4xx` тестовых сценариев;
- p95 чтения ≤500 мс, записи ≤800 мс;
- CPU p95 <70%, RAM <75%, swap-in/out отсутствует;
- PostgreSQL pool не исчерпан, lock waits и slow queries объяснены;
- после пика latency возвращается к норме не более чем за 2 минуты;
- backup/restore и deployment не приводят к OOM или потере данных.

Результат сохраняет версии image/VM/PostgreSQL, seed profile, RPS, latency,
ошибки, CPU/RAM/I/O и вывод по максимальной безопасной нагрузке. Только этот
отчёт может подтвердить либо скорректировать выбранную VM.

Локальная приёмка и воспроизводимый runner зафиксированы в
[`r1-load-capacity-report.md`](../qa/r1-load-capacity-report.md). Она подтвердила
0% ошибок и read p95 101,26 ms при 100 VU / 50 req/s, но не заменяет длительный
VPS soak из этого раздела.

## 8. Наблюдаемость

До R1 нужны графики и alerts по CPU, RAM, swap, disk, I/O wait, network,
container restarts, HTTP RPS/latency/errors, Go goroutines, PostgreSQL
connections/locks/slow queries/WAL, возрасту backup и SMTP/outbox failures.
Сырые персональные данные, email, токены и тексты проектов в метрики и логи не
попадают.

Метрики VM собираются каждые 15 минут. Ежедневно в 09:00 по `Europe/Moscow`
система отправляет каждому активному и подписанному супер-администратору одну
Telegram-сводку за предыдущие календарные сутки — с `00:00:00` до `23:59:59`
предыдущего дня по `Europe/Moscow`:

- uptime, средний/p95/максимальный CPU и RAM;
- заполнение и суточное изменение диска, I/O wait;
- health/restarts контейнеров, размер и connections PostgreSQL;
- время последнего успешного backup;
- общее количество зарегистрированных учётных записей и новые регистрации;
- число успешных авторизаций и уникальных вошедших пользователей;
- число неуспешных авторизаций и активных сессий на конец суток.

Session refresh и автоматическое восстановление сессии не являются новым
входом. В Telegram передаются только агрегаты — без логинов, ФИО, email, IP,
user ID и содержимого запросов. Получатель определяется активной ролью
супер-администратора и подтверждённой Telegram-подпиской в момент отправки, а не
зашитым `chat_id`.

Критическое событие не ждёт ежедневного отчёта. Alert создаётся после очередного
замера, если CPU или RAM выше 85% в двух последовательных замерах либо выше 95%
в одном; диск выше 80%; backup старше 26 часов; контейнер unhealthy/restarted;
либо превышен согласованный порог неуспешных входов. Событийные проверки health
контейнеров могут уведомлять раньше очередного замера. Повторные alerts
подавляются до изменения состояния; после восстановления отправляется отдельное
сообщение о нормализации.

Scheduler использует timezone-aware период, distributed lock и delivery ledger
с уникальным ключом периода/получателя. Telegram вызывается после фиксации
отчёта через outbox: недоступность Telegram не блокирует login, а restart не
создаёт вторую логическую delivery. Поскольку Telegram API не поддерживает
idempotency key, неоднозначный timeout может дать одинаковый внешний повтор;
это явно описано в monitoring contract. Период, час отправки и пороги задаются
конфигурацией.

## 9. Ограничения анализа

Текущие характеристики production VM автоматически проверить не удалось:
сервер отклонил неинтерактивную SSH-аутентификацию. Поэтому документ не заявляет,
что существующая VM уже соответствует рекомендации. Перед изменением тарифа
нужно снять `nproc`, `free -h`, `df -h`, `docker stats`, `docker system df` и
PostgreSQL metrics, затем сравнить их с порогами выше.
