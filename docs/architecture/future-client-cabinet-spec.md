# Кабинет заказов и проектное взаимодействие — спецификация для согласования

> Статус: **черновик для согласования**. Документ описывает планируемое поведение и не означает, что функциональность уже доступна на production.

## 1. Цель

Создать защищённый кабинет для ведения заказов по дизайн- и архитектурным проектам. Внутри заказа пользователи работают с задачами, сроками, календарём, реестром материалов и историей действий. Доступ к каждой сущности определяется не только типом пользователя, но и его привилегиями **в конкретном заказе**.

Публичное портфолио и анонимная контактная форма остаются доступными без учётной записи. Кабинет располагается в отдельной защищённой зоне `/account`.

## 2. Термины

| Термин | Значение |
| --- | --- |
| Заказ | Рабочее пространство одного объекта/проекта, созданное заказчиком или супер-администратором; может временно существовать без назначенного заказчика. |
| Создатель заказа | Пользователь, создавший заказ; всегда сохраняется в аудите, но сам факт создания не назначает роль заказчика. |
| Заказчик | Необязательный участник заказа с клиентскими правами: видит весь свой заказ, комментирует и принимает результат, но не удаляет заказ. |
| Супер-админ | Учётная запись с доступом ко всем заказам и правом удалить заказ. |
| Администратор заказа | Пользователь с полным управлением одним назначенным заказом; не может удалить сам заказ. Таких пользователей может быть несколько. |
| Исполнитель | Участник, которому назначена задача. По умолчанию видит только назначенные ему задачи. |
| Профессиональная роль | Профильная характеристика: заказчик, дизайнер, прораб, архитектор и будущие роли. Сама по себе не открывает данные. |
| Привилегия | Разрешение на действие в одном заказе: просмотр материалов, изменение дедлайна, удаление записи и т. п. |

## 3. Пользователи и авторизация

### 3.1 Регистрация

Форма регистрации содержит:

| Поле | Обязательное | Правило |
| --- | --- | --- |
| Логин | Да | Уникален без учёта регистра. |
| Email | Да | Уникален без учёта регистра; подтверждается отдельно, если регистрация активирована через Telegram. |
| Имя | Да | От 1 символа после нормализации. |
| Фамилия | Нет | Необязательное профильное поле. |
| Отчество | Нет | Необязательное профильное поле. |
| Профессиональная роль | Да | Выбор из действующего справочника ролей. |
| Пароль | Да | 15–128 символов; локальная проверка на скомпрометированные и слабые пароли по R1 security ADR. |
| Подтверждение пароля | Да | Должно совпадать с паролем. |

Справочник профессиональных ролей хранится в базе. Начальные значения: `Заказчик`, `Дизайнер`, `Прораб`, `Архитектор`. Супер-админ может добавлять, отключать и переименовывать роли. Система поддерживает несколько ролей в профиле, даже если на первом экране регистрации выбирается одна основная.

### 3.2 Вход и сессия

В header отображается кнопка «Войти». После входа она заменяется на меню профиля и ссылку в кабинет.

- Вход выполняется по логину и паролю; email может быть добавлен как альтернативный идентификатор в последующей версии.
- Пароль пользователей хранится только как хеш Argon2id.
- Сессия является непрозрачной серверной записью. В браузер выдаётся cookie `__Host-arhdesign_session`: `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, без `Domain`.
- Сессия: 8 часов бездействия, максимум 24 часа; идентификатор обновляется после входа и смены привилегий.
- Для мутаций требуется same-origin/CSRF-проверка.
- Нужны подтверждение регистрации через email/Telegram, отдельный статус
  подтверждения email, восстановление пароля через ранее подтверждённый канал,
  ограничение попыток входа и журнал событий безопасности.

### 3.3 Супер-админ и Telegram

Учетные данные `ADMIN_USERNAME` и `ADMIN_PASSWORD`, хранимые в секретах GitHub/VPS, сохраняют роль логина и пароля администратора Telegram-бота. При успешном входе этими данными создаётся сессия `super_admin`; пароль в базу не записывается.

Это связывает доступ супер-админа с паролем бота. В будущем рекомендуется разделить секреты бота и супер-администратора, но текущая спецификация поддерживает согласованное требование об одинаковом пароле.

### 3.4 Telegram-уведомления пользователей

Любой зарегистрированный и авторизованный пользователь может связать личный чат с Telegram-ботом и получать уведомления о событиях, которые относятся к доступным ему заказам и задачам.

Первый сценарий связи в боте подтверждает pending account по login/password:

1. после регистрации пользователь выбирает `Telegram` на сайте и переходит по
   ссылке `t.me/<bot>?start=register`;
2. сайт не показывает и не принимает login/password: выбор канала сразу
   открывает приложение Telegram в чате с ботом; web остаётся только fallback;
3. бот только в личном chat последовательно запрашивает login и password,
   указанные при регистрации;
4. Identity service применяет ту же password verification и rate-limit policy,
   что web login, но pending account может пройти только сценарий подтверждения;
5. при успехе одна транзакция переводит account в `active`, создаёт связь
   `user_id ↔ telegram_chat_id`, отзывает email verification tokens и пишет
   allowlisted audit event;
6. бот отвечает «Профиль подтверждён» без дополнительной ссылки; при ошибке не
   уточняет неверное поле и не раскрывает наличие account.

Login допускается только в краткоживущем состоянии диалога с TTL 5 минут.
Password обрабатывается только в памяти одного запроса, не пишется в БД, logs,
audit или outbox. Бот немедленно вызывает `deleteMessage` для исходного password-
сообщения при успехе и ошибке; неуспешное удаление наблюдается и повторяется в
ограниченном бюджете. Для первой версии подключение допускается только в личном
чате, а не в группе или канале.

Владелец продукта принимает residual risk: до удаления сообщение с password
проходит через инфраструктуру Telegram, а приложение не может доказать удаление
всех технических копий на стороне внешнего сервиса. Этот факт должен быть явно
показан пользователю перед вводом password и отражён в документах о ПДн.

После подтверждения через Telegram account активируется, но email остаётся
`unverified` до отдельного подтверждения в настройках. Восстановление доступа
через Telegram разрешено только для active chat binding, созданного до запроса;
email-восстановление — только для подтверждённого email. Публичный ответ для
неизвестного account, неподтверждённого email и отсутствующего binding одинаков.

Связанный пользователь может через меню бота или настройки кабинета: посмотреть статус подписки, выбрать типы уведомлений, временно приостановить их и отписаться. Повторная подписка того же пользователя в новом личном чате заменяет старую связь только после успешной проверки учётных данных.

События первой версии:

- назначение пользователя исполнителем задачи, перенос дедлайна, изменение статуса и запрос на проверку;
- новый комментарий в доступной пользователю задаче или заказе;
- события календаря доступных задач, сроков, поставок и встреч;
- изменения материалов и поставок — только при `materials.view`;
- изменения финансовых операций и подтверждающих файлов — только при `financials.view`.

Перед каждой отправкой сервер заново проверяет доступ получателя к заказу и сущности. Если пользователь исключён из заказа, его привилегия отозвана, задача переназначена или подписка отключена, сообщение не отправляется. Это предотвращает утечку названий проектов, сроков, сумм и других данных через уже связанный Telegram-чат.

### 3.5 Управление пользователями супер-администратором

В глобальной области для роли `super_admin` доступна страница «Пользователи». Она показывает список всех учётных записей с именем, логином и email, профессиональной ролью, датой регистрации, временем последней активности, статусом доступа и количеством активных проектов. Страница недоступна другим ролям и защищается серверной проверкой `users.manage`.

Для `super_admin` также доступен раздел «Сводки по задачам». Он агрегирует задачи по проектам и сотрудникам за выбранный календарный месяц. Доступ к разделу и каждому запросу защищается правом `reports.tasks.manage`.

Супер-администратор может временно отключить или повторно включить доступ пользователя к платформе. Отключение требует явного подтверждения и причины, немедленно завершает все активные сессии и запрещает создание новых; заказы, история и аудит не удаляются. Нельзя отключить последнего активного супер-администратора. Каждое изменение статуса фиксирует инициатора, дату, причину и прежнее значение в журнале аудита.

## 4. Модель доступа

### 4.1 Основное правило

Профессиональная роль не является правом доступа. Доступ задаётся сочетанием:

1. супер-админ — доступ ко всем заказам;
2. назначенный заказчик — базовые клиентские права на свой заказ;
3. администратор заказа — полный доступ к конкретному заказу, кроме его удаления;
4. участник заказа — только выданные привилегии;
5. исполнитель задачи — минимальный доступ к назначенной задаче.

### 4.2 Привилегии заказа

| Группа | Привилегии |
| --- | --- |
| Заказ | `order.view`, `order.update_status`, `order.update`, `order.delete` |
| Участники | `members.view`, `members.manage` |
| Задачи | `tasks.view_all`, `tasks.view_assigned`, `tasks.create`, `tasks.update_all`, `tasks.update_assigned`, `tasks.assign`, `tasks.delete` |
| Комментарии и приёмка | `comments.create`, `comments.moderate`, `tasks.send_for_review`, `tasks.accept_result` |
| Материалы | `materials.view`, `materials.create`, `materials.update`, `materials.delete` |
| Календарь и сроки | `calendar.view`, `calendar.manage`, `tasks.update_deadline` |
| Финансовые данные | `financials.view`, `financials.create`, `financials.update`, `financials.delete`, `financials.approve_expenses` |

`order.delete` выдаётся только супер-админу и никогда не назначается через интерфейс. `Администратор заказа` получает все остальные привилегии соответствующего заказа. Заказчик получает просмотр всего заказа, комментарии, изменение статуса заказа, отправку задач на проверку и принятие результата, но не удаление заказа или записей.

Исполнителю по умолчанию выдаются `tasks.view_assigned`, `tasks.update_assigned` и `comments.create`. Администратор заказа или супер-админ может дополнительно выдать ему права на материалы, финансовые данные, календарь и сроки. Например, прорабу можно дать `materials.view`, `materials.create`, `materials.update`, `calendar.view` и `tasks.update_deadline` только для одного объекта.

Заказчик по умолчанию видит финансовую сводку своего заказа (`financials.view`). Создание, корректировка и удаление финансовых операций доступны только супер-админу, администратору заказа либо участнику с явно выданными `financials.*`-привилегиями. Отображение и изменение финансовых данных проходят ту же серверную проверку `Can(userID, orderID, privilege)`.

### 4.3 Проверка доступа

Каждый защищённый запрос обязан пройти серверную функцию вида `Can(userID, orderID, privilege)`.

- Для доступа к задаче дополнительно проверяются `task_id`, назначение пользователя и требуемое право.
- SQL-выборки сразу ограничиваются разрешёнными заказами и задачами; запрещено сначала получить все данные, а затем скрыть их в браузере.
- Календарь возвращает только события доступных заказов и задач. Исполнитель не получает названия, даты, счётчики или метаданные чужих задач.
- Frontend получает набор разрешённых действий и скрывает недоступные кнопки. Это удобство интерфейса, но не замена серверной проверке.
- При отказе API возвращает `403`, а при отсутствии видимой сущности — `404`, чтобы не раскрывать существование чужих данных.

Все изменения прав, назначений, статусов и финансовых записей фиксируются в журнале действий.

## 5. Заказы и задачи

### 5.1 Заказ

Заказ имеет название, описание, адрес/объект при необходимости, неизменяемого
создателя, необязательного заказчика, статус, дату создания и дату обновления.
Супер-администратор может создать и полностью вести заказ без заказчика, а
назначить или заменить заказчика позднее с обязательной записью в аудите. В
модели данных `created_by` обязателен, а активное membership типа `customer`
необязательно и может быть только одно на заказ.

Если обычный пользователь создаёт заказ через клиентский сценарий, система в
одной транзакции записывает его как `created_by` и создаёт активное membership
заказчика. Только супер-администратор может завершить создание без customer
membership.

Статусы заказа: `Новый`, `В работе`, `Приостановлен`, `На согласовании`, `Завершён`. Заказчик может менять статус своего заказа. Администратор заказа и супер-админ могут менять статус и иные поля в пределах своих прав. Удаление заказа доступно только супер-админу и выполняется как мягкое удаление с обязательной записью в аудите.

### 5.2 Задача

Задача принадлежит одному заказу и содержит название, описание, статус, дедлайн, ответственных, фактические `started_at` и `completed_at`, дату проверки, дату принятия и историю.

Статусы задачи: `Новая`, `В работе`, `На проверке`, `Нужны доработки`, `Принята`.

Время старта фиксируется при первом переходе в `В работе`, время завершения — при фактическом окончании. Административная корректировка требует причины и записи в аудите. Выплаты хранятся отдельными строками по исполнителю, сумме и валюте; управлять ими может только `super_admin`.

- Исполнитель изменяет рабочий статус своей назначенной задачи и добавляет результат.
- Заказчик комментирует, отправляет на проверку, запрашивает доработки и принимает результат при наличии соответствующей привилегии. Если заказчика нет, проверку и приёмку выполняет супер-администратор либо участник с явно выданной привилегией.
- Администратор заказа и супер-админ управляют задачами и назначениями полностью.
- На одну задачу можно назначить несколько исполнителей; каждому видна эта задача, но не остальные задачи заказа без дополнительного права.

### 5.3 Глобальные чаты и обсуждения проекта

В глобальной области кабинета доступен раздел **«Чаты»** для личных и групповых диалогов между зарегистрированными пользователями. Новый чат создаётся через поиск активной учётной записи по точному логину или email. Для группового чата обязательно имя; личный диалог отображается по имени собеседника. Поиск ограничивается по частоте и не должен позволять массовое перечисление пользователей. Глобальный чат сам по себе не предоставляет доступ к проектам и их данным.

У каждого заказа также есть собственный **общий чат проекта** для координации его участников. Он является отдельным от глобальных диалогов и недоступен пользователям, не входящим в проект. В общем чате допускаются сообщения, относящиеся к заказу в целом; они не видны участникам других проектов.

Также создаются контекстные обсуждения, обязательно связанные с предметом работы: задачей, материалом, запросом на расход, финансовой операцией, счётом, поставкой или другим разрешённым событием проекта. Из общего чата и из карточек сущностей можно перейти в связанное обсуждение; сообщение показывает ссылку на материал, расход или задачу, если такая связь есть.

Таблицы задач, материалов и расходов предоставляют действие `Обсудить`, которое открывает существующий чат сущности или атомарно создаёт единственный контекстный чат. Уникальность обеспечивается по `(order_id, context_type, context_id)`. Участник чата не получает дополнительных прав: доступ повторно вычисляется из проекта и связанной сущности.

В сообщении сохраняются `order_id`, тип и ID связанной сущности, автор, текст, дата и история изменений. Пользователь видит обсуждение только если сохраняет доступ и к заказу, и к связанной сущности. Уведомления Telegram о комментариях используют тот же контекст и не раскрывают данные недоступной задачи или расхода.

Первый реализованный контекстный срез охватывает задачи, материалы и запросы на
расход. Имя обсуждения обязательно и фиксируется при первом атомарном создании;
повторное действие возвращает существующий чат. Проверка доступа выполняется на
backend при создании, чтении и отправке, а не только при отображении действия в
интерфейсе. Контракт и границы зафиксированы в
`client-cabinet-contextual-chat-adr.md`.

## 6. Реестр материалов и оплат

### 6.1 Назначение

Внутри заказа доступен раздел «Материалы и оплаты». Он заменяет ручную таблицу поставщиков и хранит исходные записи в нормализованном виде. Табличное представление группирует данные по категориям и поставщикам, показывает итоги и исключает ручные расхождения сумм.

### 6.2 Структура

```text
Заказ
└─ Категория материалов
   └─ Поставщик / договор
      ├─ контактные данные
      ├─ сумма договора
      ├─ счета
      ├─ оплаты
      ├─ поставки и монтаж
      └─ примечания
```

Поля поставщика/договора: категория, поставщик или предмет договора, контактная информация, сумма договора, номер и дата счёта, описание, примечание, статус оплаты, статус поставки.

У одного договора может быть много оплат: аванс, доплата, доставка, монтаж. Каждая оплата содержит сумму, дату, счёт и комментарий. Общая оплаченная сумма и остаток вычисляются сервером: `сумма договора − сумма подтверждённых оплат`.

### 6.3 Статусы и даты доставки

Для каждой поставки хранятся:

- статус: `Ожидается`, `Частично доставлено`, `Доставлено`, `Установлено`, `Отменено`;
- плановая дата доставки;
- фактическая дата доставки;
- при необходимости отдельная дата монтажа/установки.

Плановая дата используется до доставки; фактическая фиксируется при статусе «Доставлено». Изменение статуса и любой даты отражается в журнале и календаре заказа.

### 6.4 Редактирование и удаление

Создание, изменение и удаление доступны только при соответствующих `materials.*`-привилегиях. Удаление — мягкое: запись скрывается из рабочего реестра, но остаётся в аудите со снимком значений, автором, временем и причиной удаления. Финансовые итоги не учитывают удалённые записи.

### 6.5 Финансовая сводка заказа

На главной странице каждого заказа отображается сводка движения денег по этому заказу:

- **Поступления от заказчика** — сумма подтверждённых денежных поступлений, внесённых заказчиком;
- **Расходы** — сумма подтверждённых расходов по поставщикам, материалам, доставке, монтажу и иным статьям заказа;
- **Остаток средств** — `подтверждённые поступления − подтверждённые расходы`;
- **Движение средств** — список операций с датой, типом (`поступление`, `расход`, `корректировка`, `возврат`), суммой, статьёй, контрагентом/плательщиком, статусом подтверждения, автором и комментарием.

В интерфейсе используются именно термины «поступления от заказчика» и «расходы», чтобы не смешивать проектный денежный поток с бухгалтерским доходом предпринимателя. Это управленческий реестр по объекту, а не налоговый или бухгалтерский учёт.

Для заказа без назначенного заказчика заголовок меняется на «Поступления по
проекту», а плательщик указывается в конкретной операции. Отсутствие заказчика
не меняет формулу остатка и не создаёт фиктивного пользователя-плательщика.

В сводку и остаток включаются только операции со статусом `Подтверждено`; черновики, отменённые операции и мягко удалённые записи не влияют на итог. Нельзя изменить или удалить подтверждённую операцию без записи в аудите; корректировка оформляется отдельной операцией с причиной и ссылкой на исходную запись.

### 6.6 Детальная страница финансов и подтверждающие файлы

Для каждого заказа создаётся отдельная страница `/account/orders/[orderId]/financials`. На ней доступны:

- фильтры по периоду, типу операции, статье, контрагенту и статусу;
- таблица/лента всех операций с поступлениями, расходами, возвратами и корректировками;
- карточка выбранной операции с исходной суммой, датой, контрагентом, связью с договором или поставкой, автором и журналом изменений;
- создание и редактирование операций для пользователей с соответствующими `financials.*`-правами;
- прикрепление одного или нескольких подтверждающих файлов к расходу: чека, счёта, акта, платёжного поручения, договора или иного документа.

Вложения принадлежат конкретной финансовой операции и хранят метаданные: исходное имя, MIME-тип, размер, хеш, дату загрузки, пользователя-загрузчика, статус проверки и ссылку на объектное хранилище. В первой версии допустимы PDF, JPG, PNG, WEBP, DOCX и XLSX; лимит размера и итоговый перечень форматов утверждаются перед разработкой. Файлы не отдаются по постоянному публичному URL: API выдаёт краткоживущую подписанную ссылку только после проверки доступа к заказу и `financials.view`.

Загрузка допускается при `financials.create` или `financials.update`; удаление вложения — при `financials.delete`. Удаление мягкое и не уничтожает аудиторский след. Перед доступом файл проходит проверку типа, ограничения размера и антивирусную проверку; неуспешно проверенные файлы недоступны пользователям. Каждая загрузка, просмотр через API, замена и удаление записываются в аудит.

### 6.7 Запросы на расход и согласование заказчиком

Участник с `financials.create` может создать **запрос на расход**: сумму, описание, статью расхода, поставщика при наличии, ссылку на задачу/материал/договор и подтверждающие файлы или счёт. Запрос не является оплатой и не уменьшает остаток средств до фиксации фактического платежа.

У запроса предусмотрены статусы: `Черновик`, `Ожидает согласования`, `Автосогласован`, `Согласован`, `Отклонён`, `Ожидает оплаты`, `Оплачен`, `Отменён`. Решение о согласовании сохраняет автора, дату, комментарий и снимок суммы. При изменении суммы, статьи, контрагента или счёта после согласования создаётся новая версия запроса, требующая повторного согласования.

В настройках каждого заказа есть переключатель **«Автосогласование расходов»**. Он включён по умолчанию для нового заказа. Когда он включён, новый запрос получает статус `Автосогласован`, но назначенный заказчик при наличии всё равно получает уведомление и может просмотреть операцию. Когда переключатель выключен, запрос получает статус `Ожидает согласования`; заказчик, супер-администратор или участник с `financials.approve_expenses` может согласовать или отклонить его с комментарием. Отсутствие заказчика не блокирует работу заказа и не переводит запрос в недостижимое состояние. Включение, выключение и все решения фиксируются в аудите.

Связь с реестром материалов строится по состояниям, а не по ручному дублированию:

1. запрос, связанный с материалом/поставщиком, создаёт черновик счёта;
2. согласованный или автосогласованный запрос разрешает оплату, но не считается расходом до подтверждения платежа;
3. после статуса `Оплачен` создаётся подтверждённая финансовая операция типа `расход` и активная запись счёта/оплаты в реестре материалов;
4. отклонённые, отменённые и неоплаченные запросы не попадают в итоговую таблицу материалов и не влияют на финансовую сводку.

Таким образом, реестр материалов показывает согласованные с заказчиком и фактически оплаченные счета; черновики и ожидающие согласования запросы доступны только на странице финансов и в журнале согласования.

### 6.8 Прямая связь материалов и расходов

Материал и расход связаны двусторонне: запрос на расход может содержать `material_id`, а карточка материала показывает все связанные запросы, оплаты и финансовые операции. Для одного расхода допускается несколько материалов с количеством и распределённой суммой; для одного материала — несколько расходов (например, счёт, доплата, доставка). Сумма подтверждённого платежа одновременно отображается в финансовой сводке и в истории оплат материала, без ручного дублирования.

Удаление или изменение связи не удаляет финансовую операцию: создаётся новая версия связи с причиной и записью в аудите. Если расход или материал обсуждается, контекстное обсуждение сохраняет ссылки на оба объекта и доступно через общий чат проекта.

## 7. Календарь и сроки

Календарь доступен до выбора проекта как общий рабочий экран и имеет представления «Месяц», «Неделя» и «Список». Пользователь фильтрует события по одному или нескольким доступным проектам; при переходе из проекта фильтр уже содержит этот проект. На мобильных устройствах основным является список с группировкой по датам; все элементы доступны с клавиатуры и имеют текстовые статусы, а не только цветовую маркировку.

Из календаря пользователь с соответствующими правами может создать самостоятельное событие или новую задачу. Создание задачи требует указания проекта и ответственного, а событие — проекта, даты/времени и типа; обе операции сразу отражаются в календаре и журнале заказа.

### 7.1 Источники событий

| Источник | События |
| --- | --- |
| Заказ | Старт, сдача объекта, встреча, выезд, этап проекта, произвольное событие. |
| Задача | Дедлайн исполнителя, проверка, принятие, перенос срока. |
| Материалы | Плановая и фактическая доставка, монтаж, установка. |

Типы календарных событий: `Событие`, `Этап проекта`, `Срок сдачи объекта`, `Дедлайн задачи`, `Поставка`, `Монтаж/установка`.

Дедлайн задачи — единственный источник правды: изменение даты в задаче обновляет календарь, а изменение системного календарного события обновляет задачу. Самостоятельные события хранятся только в календаре. Это исключает два несинхронных срока.

В календаре применяются те же права, что и в заказе. Исполнитель видит только события своих задач и разрешённых материалов; заказчик видит все события своего заказа; администратор заказа и супер-админ — все события в доступной области.

## 8. Интерфейсы

### 8.1 Навигация

До входа в header остаются элементы публичного сайта. После входа header не содержит навигационных ссылок: в нём остаются бренд, профиль пользователя, меню с настройками и выходом. Это исключает смешивание публичной и рабочей навигации.

Глобальная защищённая область до выбора проекта содержит `Проекты`, общий `Календарь` (`/account/calendar`) и `Чаты` (`/account/chats`). Для `super_admin` дополнительно показывается пункт `Пользователи`. Отдельного раздела «Обзор» нет. Общий календарь фильтруется по доступным проектам и ведёт к связанной задаче или проекту.

После входа в проект глобальная навигация целиком заменяется левой контекстной навигацией этого проекта. В её верхней части находится кнопка `← Назад к проектам`, возвращающая к сохранённому состоянию списка. Ниже располагаются:

1. `Сводка`;
2. `Задачи`;
3. `Календарь проекта`;
4. `Материалы`;
5. `Финансы проекта`;
6. `Чат проекта`.

Материалы и финансы не существуют как глобальные страницы: каждый их маршрут обязательно содержит `orderId`. Календарь может быть открыт глобально с фильтром по проектам или в контексте одного проекта. Текущая страница выделяется текстом и индикатором; хлебные крошки и кнопка «Назад к проектам» сохраняют фильтры и позицию списка.

| Маршрут | Назначение |
| --- | --- |
| `/login` | Вход, ссылка на регистрацию и восстановление пароля. |
| `/register` | Регистрация пользователя. |
| `/account` | Список доступных проектов. |
| `/account/calendar` | Общий календарь с фильтром по доступным проектам, созданием события или задачи и переходом к связанному контексту. |
| `/account/chats` | Личные и групповые чаты; создание чата по логину или email активного пользователя. |
| `/account/users` | Реестр пользователей, активность и управление статусом доступа; только для `super_admin`. |
| `/account/projects/new` | Создание проекта, необязательное назначение заказчика и назначение администраторов заказа. |
| `/account/reports/tasks` | Таблица задач сотрудников и месячные итоги по времени и выплатам; только для `super_admin`. |
| `/account/reports/tasks/new` | Конструктор сводки с выбором месяца, проектов/сотрудников и сохранением фильтра как шаблона. |
| `/account/orders/[orderId]` | Стартовая страница проекта с задачами, статусом, участниками и финансовой сводкой поступлений, расходов и остатка. |
| `/account/orders/[orderId]/tasks` | Список задач проекта с фильтрами, сроками и ответственными. |
| `/account/orders/[orderId]/tasks/[taskId]` | Карточка задачи, комментарии, результат, сроки и статусы. |
| `/account/orders/[orderId]/materials` | Реестр материалов, оплат, поставок и итогов. |
| `/account/orders/[orderId]/financials` | Детальный денежный поток: поступления, расходы, остаток, операции и подтверждающие файлы. |
| `/account/orders/[orderId]/expense-requests/new` | Создание нового расхода: сумма, статья, поставщик, связь с задачей или материалом и вложения. |
| `/account/orders/[orderId]/calendar` | Календарь проекта. |
| `/account/orders/[orderId]/chat` | Общий чат проекта и вход в контекстные обсуждения сущностей проекта. |
| `/account/orders/[orderId]/members` | Участники и привилегии; только при `members.manage`. |
| `/account/orders/[orderId]/discussions/[contextType]/[contextId]` | Обсуждение конкретной задачи, расхода, счёта, поставки или другого события проекта. |

Все кнопки действий отображаются только при наличии соответствующей привилегии. Формы обязаны показывать ясные поля, ошибки около поля, состояние сохранения и понятный результат действия. Действия удаления требуют отдельного подтверждения и обязательного текстового объяснения.

## 9. Данные и миграции

До реализации каждого релиза схема данных проектируется и согласуется отдельно:
ERD размещается на странице Figma `09 — Client Cabinet / Data Model`, а
версионируемая Mermaid ERD и data dictionary хранятся в репозитории. Для каждой
таблицы фиксируются ownership, tenant scope, кардинальности, nullability,
uniqueness, foreign keys, delete policy, аудит, retention, ожидаемый рост и
обслуживаемые индексами запросы. Figma визуализирует модель, но источником
истины остаются документация и применённые миграции.

Планируемые таблицы PostgreSQL:

```text
users, professional_roles, user_professional_roles
sessions, password_reset_tokens, email_verification_tokens
telegram_subscriptions, telegram_notification_preferences, telegram_notification_deliveries
chats, chat_members, chat_messages, chat_message_attachments
orders, order_members, order_member_privileges
tasks, task_assignees, task_comments, task_activity
task_payouts
material_categories, material_contracts, material_invoices, material_payments, material_deliveries
material_expense_allocations
financial_transactions
financial_transaction_attachments
expense_requests, expense_request_versions, expense_request_attachments
calendar_events, calendar_event_sources
chat_context_links, report_filter_templates, audit_log
```

Денежные значения хранятся в `NUMERIC(14,2)` и в одной явно указанной валюте; для первой версии — RUB. Время хранится как `TIMESTAMPTZ`, даты поставок и дедлайнов без времени — как `DATE`. Все внешние ключи, индексы по `order_id` и `deleted_at`, уникальность логина/email и транзакции для оплат обязательны.

Целевая схема резервного копирования, off-site хранение, RPO/RTO и процедура
проверенного восстановления описаны в
[`postgresql-backup-and-recovery.md`](../operations/postgresql-backup-and-recovery.md).

## 10. API

Новые protected API располагаются под `/api/v1` и документируются в OpenAPI. Публичная контактная форма остаётся отдельной анонимной операцией.

Группы операций:

- `/auth/register`, `/auth/login`, `/auth/logout`, `/auth/me`, `/auth/password-reset/*`, `/auth/email-verification/*`;
- `/chats`, `/chats/{chatId}`, `/chats/{chatId}/members`, `/chats/{chatId}/messages`;
- `/account/telegram-subscription`, `/account/notification-preferences`;
- `/orders`, `/orders/{orderId}`, `/orders/{orderId}/members`, `/orders/{orderId}/privileges`;
- `/orders/{orderId}/tasks`, `/tasks/{taskId}`, `/tasks/{taskId}/comments`, `/tasks/{taskId}/assignees`;
- `/orders/{orderId}/materials/*`, `/material-contracts/{contractId}/payments`, `/material-contracts/{contractId}/deliveries`;
- `/orders/{orderId}/financial-summary`, `/orders/{orderId}/financial-transactions`, `/financial-transactions/{transactionId}`;
- `/financial-transactions/{transactionId}/attachments`, `/financial-transaction-attachments/{attachmentId}`;
- `/orders/{orderId}/expense-requests`, `/expense-requests/{requestId}`, `/expense-requests/{requestId}/approve`, `/expense-requests/{requestId}/reject`;
- `/orders/{orderId}/settings/expense-approval`;
- `/orders/{orderId}/calendar`, `/calendar-events/{eventId}`;
- `/orders/{orderId}/audit`.

Запросы на создание, изменение или удаление всегда проверяют сессию, CSRF, право, принадлежность сущности заказу и допустимость перехода статуса. Идентификаторы не должны раскрываться через предсказуемые последовательности; используются UUID.

## 11. Защита и персональные данные

- Пароли, токены сессий, reset-токены и CSRF-токены никогда не пишутся в логи.
- Вложения, если будут добавлены позднее, требуют отдельного решения по антивирусной проверке, допустимым форматам, object storage и срокам хранения.
- Телефоны/имена контактов поставщиков и финансовая информация доступны только участникам с правами; все просмотры критичных действий могут аудироваться.
- Перед запуском обновляются Политика обработки ПДн и согласие: учётная запись, профиль, данные поставщиков, материалы, финансовый реестр, история и сроки хранения.
- Применяются rate limit для регистрации/входа, безопасные заголовки, TLS, защита от CSRF, защита от перебора и принудительное завершение сессий при отзыве доступа.

## 12. Тестирование и критерии готовности

Обязательные проверки:

1. Unit-тесты всех переходов статусов, расчётов оплат и проверок привилегий.
2. Интеграционные тесты PostgreSQL: пользователь не получает чужой заказ, задачу, календарное событие или финансовую запись по прямому ID.
3. Контрактные тесты OpenAPI и негативные API-сценарии `401`, `403`, `404`.
4. E2E: регистрация, вход, заказчик, исполнитель, администратор заказа, супер-админ, отзыв доступа и мягкое удаление.
5. Проверка UI в светлой/тёмной теме, на desktop/tablet/mobile, с клавиатурой и screen reader.
6. Проверка аудита: все изменения прав, сумм, дат, статусов и удалений имеют автора и снимок изменения.

Функциональность считается готовой, если сервер гарантированно ограничивает данные и действия по заказу, frontend не показывает недоступные управляющие элементы, расчёты реестра согласованы, календарь синхронизирован с задачами/поставками, а документы по ПДн актуализированы.

## 13. Очередность реализации

Детальная поставка по версиям `0.2.0–0.8.0`, включая дизайн, документацию,
код, Cypress, визуальное ревью и полную регрессию, описана в
[`client-cabinet-release-plan.md`](client-cabinet-release-plan.md). Этот раздел
сохраняет только общий порядок технических зависимостей.

1. Создать ветку `develop` от актуального `main` и вести работу через `develop → main → release tag`.
2. Исправить текущую рассинхронизацию реквизитов согласия: Go API содержит ссылку на документ `v4`, тогда как опубликован документ `v5`.
3. Реализовать учётные записи, хеширование паролей, сессии, подтверждение email и защищённый auth API.
4. Реализовать заказы, участников, привилегии, аудит и серверную авторизацию.
5. Реализовать задачи, комментарии, статусы, приёмку и календарь.
6. Реализовать реестр материалов, оплат, поставок и финансовые расчёты.
7. Реализовать интерфейс кабинета, провести E2E/accessibility/security-проверки.
8. Обновить ПДн-документы, README, OpenAPI, миграции и инструкции развёртывания.
