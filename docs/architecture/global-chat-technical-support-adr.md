# ADR: глобальные чаты и контур технической поддержки

- Статус: accepted
- Дата: 2026-09-28
- Область: R6, Identity, Notifications, Monitoring, frontend runtime

## Контекст и пользовательские сценарии

В личном кабинете нужен глобальный раздел «Чаты», не привязанный к одному
проекту. Пользователь создаёт личный или именованный групповой чат, находит
участников по логину или электронной почте, читает историю и отправляет
сообщения. Проектные и контекстные чаты продолжают жить в границе проекта и не
смешиваются с глобальными чатами.

Одновременно платформе нужен отдельный системный пользователь — технический
администратор. Его учётная запись должна существовать в базе, иметь доступ на
уровне супер-администратора и получать в Telegram технические уведомления:

- неожиданные ошибки backend с ответом `5xx` и panic;
- runtime-ошибки frontend и необработанные отклонения Promise;
- жалобы и пожелания, отправленные из виджета поддержки в личном кабинете.

Ожидаемые ошибки пользователя (`400`, `401`, `403`, `404`, `409`, `422`,
`429`) не являются авариями и не создают Telegram-уведомление. Иначе неверный
пароль, ошибка валидации или сканирование URL создавали бы шум и позволяли
внешнему пользователю атаковать канал уведомлений. Такие ответы остаются в
агрегированных HTTP-метриках.

## Решение

### 1. Системная роль технического администратора

В `users.global_role` добавляется значение `technical_admin`. Активный
технический администратор один; частичный уникальный индекс защищает этот
инвариант. При старте API Identity выполняет идемпотентный bootstrap из
`TECH_ADMIN_USERNAME`, `TECH_ADMIN_EMAIL` и `TECH_ADMIN_PASSWORD`:

1. под advisory lock ищет учётную запись по нормализованному логину;
2. создаёт активного подтверждённого пользователя, профиль и Argon2id credential,
   если записи нет;
3. при существующей записи подтверждает роль и активный статус, но не меняет
   пароль на каждом рестарте;
4. отсутствие обязательной конфигурации при включённой авторизации считается
   ошибкой запуска, чтобы обещание «пользователь всегда в БД» не было условным.

Пароль не хранится в миграции, репозитории, логах или документации. Его смена в
будущем выполняется отдельной административной командой, а не неявным рестартом.
Технический администратор проходит обычную авторизацию и обычную Telegram-
привязку по логину и паролю. Уведомления отправляются только если привязка
активна и пользователь не отписался.

Backend считает `super_admin` и `technical_admin` привилегированными ролями для
доступа к проектам и глобальным чатам. Это решение принимается на сервере;
скрытие или отображение элементов frontend не является проверкой прав.

### 2. Глобальные чаты

Владельцем данных выступает модуль Global Chat. Он использует отдельные таблицы
`global_chats`, `global_chat_members`, `global_chat_messages`; таблицы
`chats/chat_messages` остаются владельцем проектных обсуждений.

Инварианты:

- личный чат содержит ровно двух активных участников и имеет канонический
  `direct_key`; уникальный индекс не допускает второй личный чат той же пары;
- групповой чат имеет имя длиной 2–200 символов и минимум двух участников,
  включая создателя;
- участник ищется только после аутентификации, запрос содержит минимум два
  символа и возвращает не более 20 результатов;
- обычный пользователь читает и пишет только в активный чат, где состоит;
  `super_admin` и `technical_admin` могут просматривать и модерировать все чаты;
- `client_message_id` уникален внутри чата: повтор того же запроса возвращает
  существующее сообщение, другой текст с тем же ключом даёт `409`;
- участник чата не получает никаких прав на проект или связанную сущность;
- история имеет устойчивый порядок `(created_at, id)` и cursor pagination;
- read marker принадлежит паре `(chat_id, user_id)` и обновляется монотонно.

Сохранение сообщения и создание Telegram outbox-записей происходят в одной
PostgreSQL-транзакции. Доставка Telegram выполняется worker после commit; её
ошибка не отменяет сообщение. Получатели — активные подписанные участники,
кроме автора. Привилегированный администратор, который только имеет право
просмотра, не получает каждое сообщение автоматически.

### 3. Технические события и обратная связь

Модуль Technical Support владеет таблицей `technical_reports` и созданием
`notification_outbox` для активного `technical_admin`.

Допустимые виды отчёта:

| Вид | Источник | Сохраняемые данные |
| --- | --- | --- |
| `backend_error` | HTTP middleware после ответа `5xx` или recovery panic | request ID, метод, шаблон/нормализованный путь без query, status, безопасный код, fingerprint, время |
| `frontend_error` | error boundary, `window.error`, `unhandledrejection` | path без query, ограниченное безопасное сообщение, digest/fingerprint, время, nullable actor |
| `feedback` | виджет личного кабинета | категория `complaint`/`suggestion`, текст пользователя, path без query, actor, время |

Запрещено сохранять или отправлять: тело HTTP-запроса/ответа, query string,
пароль, токен, cookie, CSRF, Telegram chat ID, IP, заголовки авторизации, текст
переписки, SQL, полный URL, произвольные server stack traces. Frontend stack
может использоваться только локально для вычисления fingerprint и не уходит в
API. Сообщение feedback является пользовательским содержимым и хранится отдельно
от технического payload; интерфейс предупреждает не указывать пароли, платёжные
данные и другие секреты.

Frontend-отчёты и feedback принимаются только из same-origin браузера.
Feedback доступен аутентифицированным пользователям. Backend повторно проверяет
сессию, CSRF, длину/enum и применяет лимит на пользователя. Frontend runtime
report допускается для текущей сессии; без действующей сессии ошибка остаётся в
локальном console и общей инфраструктурной метрике. Это предотвращает открытый
анонимный канал спама в Telegram.

Одинаковые автоматические ошибки агрегируются по `fingerprint` в временном окне:
первое событие создаёт уведомление, повторы увеличивают счётчик. Feedback не
дедуплицируется. Если запись отчёта или outbox недоступна, исходный пользовательский
ответ уже сформирован и не меняется; middleware пишет только безопасный локальный
лог с request ID и классом ошибки.

### 4. UI

`/account/chats` использует глобальную навигацию личного кабинета. На desktop
экран делится на список чатов и активный разговор; на узком экране показывается
один уровень с предсказуемой кнопкой назад. Создание чата — modal dialog:

- тип «Личный» или «Групповой»;
- имя обязательно только для группового;
- поиск участников через общий `Autocomplete`, выбранные участники доступны
  клавиатурой и могут быть удалены;
- loading, empty, error, retry, disabled и success состояния обязательны.

Кнопка поддержки закреплена справа снизу в личном кабинете, не перекрывает
основные действия и сохраняет позицию на всех страницах. Dialog содержит
категорию, сообщение, предупреждение о секретах, ссылку на политику и явные
состояния отправки. Icon-only control имеет accessible name, tooltip, видимый
focus; контент не полагается только на цвет.

Error boundary показывает безопасное сообщение и кнопку повторной попытки.
Отправка отчёта выполняется один раз на fingerprint в пределах вкладки и не
задерживает восстановление UI.

## Транзакции, отказ и восстановление

- Bootstrap технической учётной записи — одна транзакция под advisory lock.
- Создание чата, участников и audit event — одна транзакция.
- Сообщение, audit event и outbox intents — одна транзакция.
- Technical report и его outbox intents — одна транзакция.
- Внешний Telegram-вызов никогда не выполняется внутри этих транзакций.
- Повтор миграции безопасен на пустой и заполненной PostgreSQL; удаление новых
  таблиц является допустимым rollback только до появления полезных данных.
  После cutover recovery — forward fix или восстановление из проверенного backup.

## Индексы и ожидаемые запросы

- inbox: membership equality по `user_id`, active chat, порядок последней
  активности; индекс `(user_id, left_at, chat_id)` и chat activity index;
- history: equality `chat_id`, range/order `(created_at DESC, id DESC)`;
- idempotency: unique `(chat_id, client_message_id)`;
- direct uniqueness: partial unique `direct_key WHERE kind='direct'`;
- reports: fingerprint + aggregation window и retention order;
- technical recipient: partial unique active `global_role='technical_admin'`.

На локальной тестовой выборке планы могут законно выбрать sequential scan.
Перед production-оптимизацией планы повторно измеряются на репрезентативном
объёме; данный ADR не обещает конкретную latency без такого измерения.

## Проверка и критерии приёмки

- миграция проходит на пустой и заполненной PostgreSQL и сохраняет старые чаты;
- два конкурентных bootstrap не создают двух технических администраторов;
- обычный пользователь не читает чужой чат; обе глобальные роли читают его;
- повтор `client_message_id` не дублирует сообщение;
- отозванный участник немедленно теряет чтение, запись и Telegram-доставку;
- тесты redaction подтверждают отсутствие запрещённых данных в report metadata,
  ciphertext plaintext fixture, логах и Telegram message;
- `5xx` создаёт report/outbox, ожидаемый `4xx` — нет;
- feedback требует session + CSRF, ограничивает частоту и доходит только
  привязанному техническому администратору;
- Cypress покрывает создание личного/группового чата, общение двух пользователей,
  запрет третьему, feedback и recoverable frontend error;
- component checks выполняются в обеих темах и на 1440/768/390 px.

## Последствия и границы текущего этапа

Polling остаётся текущим delivery transport, как в проектном чате; SSE/WebSocket
рассматривается после измерения нагрузки. Файлы, редактирование/удаление сообщений,
presence и полнотекстовый поиск истории не входят в этот этап. Техническая роль
не даёт права обходить криптографическую защиту секретов и не превращает браузер
в доверенную границу.
