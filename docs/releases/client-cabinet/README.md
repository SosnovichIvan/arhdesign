## Как работать со списком

1. До начала кода оформить изменение в OpenSpec и связать его задачи с ID из
   соответствующего файла этого каталога.
2. Выполнять блоки по порядку. Задачу с зависимостями нельзя начинать, пока
   зависимости не закрыты или явно не зафиксировано согласованное исключение.
3. Отмечать `[x]` только после появления указанного результата и проверяемого
   доказательства: Figma Node ID, ссылка на документ/миграцию/тест, команда и
   результат проверки либо ссылка на CI.
4. Если обязательная функция переносится, оставить задачу открытой, записать
   решение и обновить план версии. Молчаливое уменьшение объёма запрещено.
5. Публиковать релиз только после закрытия всех задач раздела «Приёмка релиза».

## Обозначения и порядок

ID имеет вид `R<номер>-<область>-<номер>`:

- `SPEC` — требования и OpenSpec;
- `DES` — Figma, пользовательские пути и состояния;
- `DATA` — ERD, словарь данных, миграции и запросы;
- `API` — backend-контракты, права и внешние эффекты;
- `FE` / `BE` — frontend/backend реализация;
- `TEST` — unit, component, integration и контрактные тесты;
- `E2E` — Cypress и существующая Playwright-регрессия;
- `QA` — визуальная проверка, доступность и ручной smoke;
- `OPS` — backup, restore, наблюдаемость и rollback;
- `DOC` — продуктовая и эксплуатационная документация;
- `REL` — PR, тег, deployment и контроль после выпуска.

В каждом файле `Depends on` ссылается на ID задач этого или предыдущего релиза.
`Evidence` заполняется при выполнении фактической ссылкой или командой, а не
словом «готово».

## Общий release gate

Для каждого релиза обязательны:

- согласованные маршруты и состояния в Figma для 1440, 768 и 390 px, обе темы;
- схема данных в Figma и версионируемые Mermaid ERD/data dictionary;
- серверная проверка роли, project scope и привилегии на каждый запрос;
- совместимая PostgreSQL-миграция и проверка обновления с предыдущей версии;
- минимум 90% строк и ветвей изменённого авторского кода там, где метрика
  поддерживается, без искусственного исключения доменной логики;
- Cypress по путям релиза и полный прогон старых Vitest/Playwright/Go тестов;
- visual review, keyboard/focus, axe, reduced-motion и Docker smoke-test;
- свежий backup перед миграцией и подтверждённое восстановление по
  [плану backup/recovery](../../operations/postgresql-backup-and-recovery.md);
- рабочая ветка → PR в `develop` → PR `develop` в `main` → неизменяемый SemVer
  tag на коммите из `main`.

Невыполненный пункт этого gate блокирует выпуск, даже если happy path работает.
