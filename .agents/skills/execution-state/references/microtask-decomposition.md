# Semantic chunks

Semantic chunk — минимальный законченный результат, который можно проверить и
безопасно передать новому context. Это не отдельная команда и не обязательное
соответствие одному model turn.

## Декомпозиция

1. Возьми одну leaf-задачу OpenSpec либо один проверяемый результат standalone-
   запроса.
2. Определи `affected_areas`, ограниченные `reads` и `writes`, зависимости и
   границы полномочий.
3. Сформулируй 1–5 наблюдаемых `done_when`, затрагиваемые публичные
   `contracts` и именованные `regression_checks`.
4. Назначь `cohesion_key`: соседние chunks с одним ключом выгодно выполнять в
   одном context. Не используй ID задачи как ключ, если несколько шагов меняют
   одну и ту же модель или подсистему.
5. Объедини реализацию с её узкой проверкой.
6. Раздели работу, если внутри несколько независимо проверяемых результатов,
   разные подсистемы или несвязанные способы проверки.
7. Не выделяй чтение, размышление, state update и одну shell-команду в отдельные
   chunks.

## Cross-area и bridge chunks

Если изменение пересекает несколько areas, меняет wiring, общий middleware,
schema, публичный API или data flow, пометь его `requires_bridge=true` и сразу
поставь следующим отдельный `kind=integration` chunk. Он проверяет не новую
локальную функцию, а соединение подсистем: routing/wiring, общий контракт,
сквозной happy path и отрицательный сценарий. После cross-area изменения
обычная implementation-задача не должна начинаться до integration chunk.

Каждые `review_interval` завершённых chunks controller требует
`architecture-review`. Дополнительно проводи review при появлении циклической
зависимости, быстром росте одного файла, дублировании модели или расхождении
нескольких реализаций одного контракта.

Один chunk обычно содержит несколько внутренних agent turns. Начальный ориентир
для reset-профиля — 3–8 turns, но граница адаптируется по cold-start, объёму
одноразового tool output и оставшейся работе.

## Хорошая граница

Chunk:

- имеет один сформулированный результат;
- может быть продолжен без transcript;
- оставляет проект в непротиворечивом состоянии;
- завершается evidence либо точным blocker;
- не требует переносить необработанные логи;
- ограничивает набор рабочих файлов и source refs.
- содержит проверки не только нового кода, но и ранее объявленных contracts.

Если следующий шаг зависит от незаписанной гипотезы, интерактивной сессии или
промежуточной миграции, продолжай текущий chunk. Если начинается другая
подсистема и все нужные факты уже сохранены, создай checkpoint.

## OpenSpec и standalone

В OpenSpec leaf-задачи и их статусы остаются в `tasks.md`; execution-state
хранит только active overlay. Новое обязательное требование сначала оформляется
в OpenSpec, а не добавляется скрыто в state.

В standalone компактный task index хранится отдельно от worker packet. Новая
обязательная работа не должна молча расширять пользовательский scope.

Один state поддерживает только один активный `worker_lease`, поэтому workers для
него не запускаются параллельно. Действительно независимую работу можно вынести
в отдельные state ID лишь в пределах исходного scope и permissions; результаты
каждого state всё равно принимаются его единственным coordinator по revision.
