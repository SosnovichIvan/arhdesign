# Проектирование ближайших задач и встреч

## Контракты и владельцы

Модуль `project` владеет object-scope authorization. PostgreSQL хранит
`project_tasks` и `project_meetings`; обе сущности принадлежат ровно одному
project и каскадно удаляются вместе с ним. HTTP adapter только валидирует wire
payload и отображает domain errors.

Создавать записи могут `super_admin` и active membership с ролью `customer` или
`project_admin`. Читать feed может любой active member проекта и `super_admin`.
Это временная граница до R2 granular privileges; frontend-скрытие не считается
защитой.

## Время

`due_at`, `starts_at`, `ends_at` — UTC instants (`TIMESTAMPTZ`). Встреча требует
`ends_at > starts_at`. Feed использует полуинтервал `[now, now + days)` и
ограничивает `days` значениями 1–90. Стабильный порядок: effective time, kind,
ID. У задачи effective time равен `due_at`, у встречи — `starts_at`.

## UI

Справа в заголовке блока находятся три 36-px круглые кнопки с доступными
именами и расширенной областью нажатия: задача, встреча, настройки. Формы
открываются в существующем `Dialog`; после успешного создания диалог закрывается,
feed обновляется и новая запись становится видимой. Период хранится сервером по
паре user/project, допустимы 1–90 дней, значение по умолчанию — 7. Глобальная
тема хранится отдельно на user и не дублируется по проектам.

Фильтры переносятся на новую строку и допускают wrap. Empty/error/loading и
успех выражаются текстом и содержимым, а не только цветом.

## Данные и индексы

- `project_tasks(project_id, due_at, id)` обслуживает bounded upcoming query;
- `project_meetings(project_id, starts_at, id)` обслуживает тот же query;
- `user_settings(user_id)` хранит одну тему на пользователя;
- `project_user_settings(project_id, user_id)` хранит персональный период проекта;
- запись и audit выполняются одной транзакцией;
- `version` резервируется для последующего optimistic update.

Новые таблицы пусты при rollout, backfill не нужен. Recovery — forward fix либо
удаление новых таблиц до появления production-данных; после пользовательских
записей rollback только через проверенное восстановление/экспорт данных.

## Альтернативы

Единая таблица `calendar_events` отклонена на этом шаге: задача имеет собственный
lifecycle и в R5 должна быть источником дедлайна, а не копией события. Хранение
только в браузере отклонено, потому что записи должны видеть другие участники и
сервер обязан проверять project scope.
